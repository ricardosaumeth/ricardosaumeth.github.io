How I Built a Multilingual RAG System for Under $0.0005 per Question

The architecture behind a multilingual RAG system that costs almost nothing to run

When I started architecting my new project — a multilingual AI system built on top of a RAG engine — I set myself a challenge:

Could I design a production‑grade system that costs almost nothing per question?

Most RAG stacks look like this:

  • Paid embeddings
  • Paid vector database
  • GPT‑4 for everything
  • Multiple services stitched together

It works, but it's expensive and unnecessarily complex for most use cases.

So I designed something different.

A system that costs around $0.0003 per question.

Here's the architecture.

1. Self‑Hosted Embeddings (cost: $0 per query — no per‑usage charges)

I use a multilingual sentence‑transformers model:

  • Runs locally
  • 50–100ms per embedding
  • Smaller vectors → faster search
  • Zero marginal cost
  • Works offline

And because questions repeat, I cache embeddings aggressively.

This eliminates all embedding‑related costs.

2. pgvector Instead of Pinecone/Qdrant (cost: $0)

Everything lives inside Postgres using pgvector:

  • Metadata
  • Vectors
  • Filtering
  • Similarity search

With an HNSW index, search takes 50–200ms for <100K vectors — more than enough when the LLM dominates latency.

The real win is simplicity:

  • One database
  • One backup
  • One deployment
  • No sync issues
  • No extra services

3. GPT‑4o‑mini for Generation (~$0.00027–$0.00045 per question)

This model is the sweet spot for grounded Q&A:

  • Fast
  • Cheap
  • High enough quality
  • ~200× cheaper than GPT‑4

Optimized RAG queries typically use:

  • ~600 input tokens
  • ~300 output tokens

At GPT‑4o‑mini pricing, that's roughly:

Around $0.00027 per question.

Even with larger contexts (1000 input + 500 output), the cost stays:

Under $0.0005 per question.

4. A Minimal, Cost‑Efficient Architecture

The system is intentionally lean:

  • A small FastAPI backend
  • Postgres + pgvector
  • A lightweight cache
  • A static frontend

No GPUs.
No heavy infra.
No expensive managed services.

Just a simple, unified design that scales smoothly.

Why This Architecture Works

Unification beats fragmentation

One database. One embedding model. One LLM. One deployment.

Less complexity → fewer failure modes → lower cost.

Caching is a superpower

Most questions repeat.

Caching turns a multi‑second RAG pipeline into a 100ms lookup — for free.

Choose the right LLM

RAG doesn't need GPT‑4.

It needs a model that is fast, cheap, and good at following context.

GPT‑4o‑mini hits that balance perfectly.

Multilingual without translation

Multilingual embeddings let the system avoid translation costs, latency, and errors.

The model simply answers in the user's language.

When This Approach Makes Sense

Ideal when:

  • You have <100K vectors
  • You want predictable costs
  • You want to avoid GPUs
  • You want a simple deployment
  • You want multilingual support
  • You want to scale gradually

Not ideal for:

  • Real‑time latency requirements
  • Multi‑hop reasoning
  • Massive vector datasets

But for most early‑stage products, it's the perfect balance of cost, simplicity, and performance.

The Bottom Line

You don't need:

  • Pinecone
  • GPT‑4
  • A GPU
  • A complex microservices architecture

You need:

  • pgvector
  • sentence‑transformers
  • GPT‑4o‑mini
  • A caching layer
  • A unified design

That's how you get to ~$0.0003 per question.

And that's the architecture I'm building.
